<objective>
Add explicit Docker resource governance (`deploy.resources.limits` + `reservations`) to every service in `deploy/docker-compose.production.yml`, closing audit finding P-1 / requirement INFRA-01.

Purpose: On a fixed-resource Hostinger VPS the current file has zero limits, so any single runaway container (a PDF-OCR burst in a worker, a full-collection Mongo scan, a worker memory leak) can consume all host RAM and trigger the kernel OOM killer against an arbitrary container — potentially Postgres or Mongo rather than the offender. Guaranteed datastore reservations plus tight worker caps make failures isolated and recoverable instead of cascading.

Output: An updated compose file where `docker compose config` shows memory + cpu limits on every service, datastores have reservations, workers are tightly capped, and all values are env-overridable with sane documented defaults.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host kernel → containers | Fixed VPS RAM/CPU is shared; without limits one container's demand crosses into another's working set via the OOM killer |
| operator env (`deploy/.env`) → compose runtime | Operator-supplied override values are interpolated into resource limits |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Denial of Service | any container without a limit | mitigate | Add `deploy.resources.limits.memory`/`cpus` to every service so a runaway process is capped at its own ceiling instead of exhausting host RAM |
| T-01-02 | Denial of Service | mongo / postgres-auth / redis | mitigate | Guaranteed `reservations.memory` on datastores + worker caps set below those reservations, so a bursty worker cannot get a datastore OOM-killed |
| T-01-03 | Denial of Service | operator-supplied override values | accept | An operator can set a nonsensical override (e.g. 64m for mongo) and self-inflict instability; mitigated only by documented sane defaults + comment guidance, not enforced — low risk, single trusted operator |
| T-01-04 | Tampering | compose file / no package installs | accept | This plan installs no npm/pip/cargo packages and changes only declarative resource keys; no new supply-chain surface |
</threat_model>
