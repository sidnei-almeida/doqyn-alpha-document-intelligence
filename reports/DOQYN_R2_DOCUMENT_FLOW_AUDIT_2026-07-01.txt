1. RESUMO EXECUTIVO
--------------------------------------------------------------------------------

O fluxo principal de produção (envio de documentos com IA) está implementado no
backend e segue a sequência:

  upload multipart -> análise IA em memória -> staging temporário -> confirmação
  -> persistência do original no storage -> gravação MongoDB

Com STORAGE_PROVIDER=r2 e credenciais válidas, o caminho feliz cobre:
  upload -> IA/RAG -> metadata + nome sugerido -> R2 (original intacto) -> Mongo.

Pontos fortes confirmados no código:
  - Object keys R2 opacas (documentId/versionId, sem nome original/sugerido)
  - Bucket por tenant opaco (doqyn-t-<hash12>)
  - Staging em tmp/{jobId}/original.{ext}
  - Hash SHA-256 verificado entre analyze e confirm
  - Download apenas via backend (/api/documents/download)
  - Sem VITE_R2_* e sem @aws-sdk no frontend
  - Sem presigned URL no código analisado
  - Documentos legados provider=local retornam LEGACY_LOCAL_STORAGE (410)

Lacunas relevantes em relação ao produto desejado:
  - Preview otimizado + marca d'água DOQYN: NÃO implementado
  - Versionamento real de nova versão em documento existente: UI mock, sem API
  - Listagem/download no frontend principal ainda usa MOCK_DOCUMENTS em partes
  - Provider Mongo grava "cloudflare_r2" (não literal "r2") em storage.primary
  - Staging ocorre DEPOIS da análise IA (risco se staging falhar após IA ok)
  - Upload direto (/api/documents/upload) é fluxo legado paralelo ao fluxo IA
  - slot backup (aws_s3) permanece "pending" — placeholder arquitetural
  - Auditoria de storage R2 (Put/Get/Delete/provision) não tem eventos dedicados
  - Migração local -> R2: não implementada; apenas erro controlado no download

5. UPLOAD E STAGING
--------------------------------------------------------------------------------

5.1 Endpoints

  | Endpoint                        | Arquivo                              | Função                    |
  |---------------------------------|--------------------------------------|---------------------------|
  | POST /api/ai/analyze-pdf        | api/ai/analyze-pdf.ts                | Análise + staging         |
  | POST /api/documents/confirm-analysis | api/documents/confirm-analysis.ts | Persistência final        |
  | POST /api/documents/upload      | api/documents/upload.ts              | Upload direto legado      |
  | GET  /api/documents/download    | api/documents/download.ts            | Download via backend      |
  | GET  /api/documents             | api/documents/index.ts               | Listagem/detalhe Mongo    |

  Delete/removal de arquivo no storage:
    - Rollback em confirm-analysis se insert Mongo falhar (deleteObject)
    - upload legado deleta documento Mongo se storage falhar
    - Não há endpoint público de delete de versão/documento confirmado

5.2 Onde o arquivo é recebido

  - analyze-pdf: server/utils/parseMultipart.ts via api/ai/analyze-pdf.ts
  - upload direto: parseMultipart inline em api/documents/upload.ts
  - Buffer permanece em memória durante a request

5.3 Onde é temporariamente armazenado (staging)

  Com STORAGE_PROVIDER=r2:
    - Key: tmp/{jobId}/original.{ext}
    - Bucket: doqyn-t-<hash12> (per_tenant) via ensureTenantBucket()
    - Implementação: server/storage/r2/r2StorageProvider.ts (storeStagingFile)
    - Orquestração: server/storage/stagingStorage.ts

  Com STORAGE_PROVIDER=local (legado/testes):
    - Key legada: staging/{tenantId}/{ownerUserId}/{jobId}/original.{ext}
    - Disco: LOCAL_STORAGE_ROOT

  IMPORTANTE: staging só ocorre se isStorageConfigured() === true.
  Se storage mal configurado, analyze retorna sucesso mas confirm falhará
  por ausência de staging (STAGING_FILE_NOT_FOUND ou STORAGE_NOT_CONFIGURED).

5.4 Onde o hash é calculado

  - Primeira vez: server/ai/services/analyzePdfService.ts linha ~128
    fileHash = SHA-256(buffer) no início de analyzePdfBuffer()
  - Modo no_ai: server/ai/services/noAiAnalyzer.ts (mesmo padrão)
  - Verificação no confirm: server/storage/stagingStorage.ts loadAnalysisStaging()
    recalcula SHA-256 e compara com expectedSha256 (payload.fileHash)
  - Upload direto: documentService.uploadDocument() calcula sha256 do buffer

5.5 Onde o documento é confirmado

  - API: api/documents/confirm-analysis.ts
  - Serviço: server/services/confirmAnalysisService.ts
    função confirmAnalysisPersistence()
  - Arquivo físico: persistConfirmedVersionFile() ->
    loadAnalysisStaging -> storeUploadedDocumentFile -> deleteAnalysisStaging

5.6 Onde storage.primary é montado

  - server/storage/index.ts buildVersionStorage(stored)
    R2: provider=cloudflare_r2, status=stored, objectKey, bucketAlias, storedAt
    Local: provider=local
  - Chamado por documentFileService.storeUploadedDocumentFile()

5.7 Onde Mongo é atualizado

  confirmAnalysisPersistence() insere em:
    - documents (MongoDocument)
    - documentVersions (MongoDocumentVersion) com storage, metadata, file, etc.
    - processingJobs (MongoProcessingJob)
    - auditLogs (2 eventos: metadata.confirmed + document.created)

5.8 Onde o download lê o arquivo

  - api/documents/download.ts
  - server/services/documentFileService.ts readDocumentVersionFile()
    1. Busca version no Mongo (objectKey, bucketAlias, provider)
    2. Se provider=local e R2 ativo -> LEGACY_LOCAL_STORAGE (410)
    3. getStorageProvider().readDocumentVersion(key, tenantId, bucketAlias)
    4. Retorna buffer + finalFileName/originalFileName para Content-Disposition

5.9 Frontend envolvido

  - DocumentSendPage.tsx, useBulkUploadQueue.ts
  - services/analyzePdf.ts, services/confirmAnalysis.ts
  - authFetch com credentials:include (cookie doqyn_auth)
  - NÃO há chamada frontend a /api/documents/download no src/ analisado
    (download API existe no backend; UI de listagem ainda mock)


6. ANÁLISE IA/RAG
--------------------------------------------------------------------------------

6.1 Onde ocorre

  Entrada: server/ai/services/analyzePdfService.ts analyzePdfBuffer()

  Pipeline (modo groq, AI_MODE != no_ai):
    1. validatePdfUpload
    2. extractTextFromPdf (pdf-parse)
    3. loadActiveDocumentClassRules (Mongo regras/classes)
    4. createDocumentChunks + retrievalProvider (modo "hybrid" in-memory)
    5. classifyDocumentWithRules (LLM Groq via documentClassifierAgent)
    6. extractMetadataWithRule (LLM Groq via metadataExtractorAgent)
    7. generateRecommendedFileName (documentNaming.ts — template da regra)

  Modo no_ai: server/ai/services/noAiAnalyzer.ts (sem LLM, template fixo)

6.2 RAG atual

  - server/services/retrievalProvider.ts — modo "hybrid" apenas
  - Scoring em memória (hybridChunkRetriever.ts), NÃO vector DB externo
  - Comentários indicam futuro: faiss, atlas_vector, google Document AI

6.3 Dados extraídos

  AnalyzePdfResponse inclui:
    - classification: classId, className, confidence, requiresReview, evidence
    - extraction: metadata (campos por regra), version, missingFields, reviewReasons
    - recommendedFileName (gerado por template + metadados)
    - textExtraction: pageCount, charCount, truncated
    - fileHash, fileSizeBytes, jobId, logs

6.4 O arquivo é salvo antes ou depois da análise?

  DEPOIS da análise.
  Ordem em api/ai/analyze-pdf.ts:
    analyzePdfBuffer() -> storeAnalysisStaging()
  A IA opera sobre buffer em memória; staging é persistência pós-análise.

6.5 A análise depende do arquivo em staging?

  NÃO. Depende apenas do buffer em memória durante a request.
  O confirm-analysis depende do staging (ou falha).

6.6 Nome sugerido é só metadata?

  SIM para objectKey físico.
  - generateRecommendedFileName() produz string para recommendedFileName
  - confirm grava: recommendedFileName, finalFileName, currentFileName (documento)
  - objectKey R2: documents/{documentId}/versions/{versionId}/original.pdf
  - Testes confirmam: nome sugerido não aparece no path (document-storage-flow.test.ts)

6.7 Classificação vira categoria do documento?

  SIM no fluxo confirm:
    - document.classId / className da regra Mongo
    - version.classification persistida
    - Governança usa document_classes + document_rules

6.8 Fallback quando IA falha

  - AiAnalysisError com códigos: EMPTY_FILE, FILE_TOO_LARGE, INSUFFICIENT_TEXT,
    TEXT_EXTRACTION_FAILED, AI_RATE_LIMIT, CLASS_OR_RULE_NOT_FOUND, etc.
  - status requires_review / ai_unavailable / failed no response
  - no_ai mode para dev sem Groq
  - Se classe fora das regras: requiresReview=true, extraction=null

6.9 Metadados no Mongo (versão)

  version.metadata: Record<string, MongoVersionMetadataField>
  version.metadataIndex: array indexável (string/number/date)
  document.currentMetadataPreview: preview simplificado

8. STORAGE R2
--------------------------------------------------------------------------------

8.1 Arquivos e responsabilidades

  | Arquivo                              | Responsabilidade                         |
  |--------------------------------------|------------------------------------------|
  | server/storage/r2/r2Clients.ts       | S3Client runtime vs admin                |
  | server/storage/r2/r2BucketNaming.ts  | doqyn-t-<hash12> opaco                  |
  | server/storage/r2/r2BucketProvisioner| HeadBucket/CreateBucket (admin)          |
  | server/storage/r2/r2StorageProvider.ts| Put/Get/Delete + staging               |
  | server/storage/getStorageProvider.ts | Factory com cache                      |
  | server/storage/storageKeys.ts        | Object key builders                    |
  | server/storage/stagingStorage.ts     | Orquestra staging load/store/delete    |
  | server/storage/index.ts              | buildVersionStorage, isStorageConfigured|
  | server/services/documentFileService.ts| store/read + LEGACY_LOCAL_STORAGE       |
  | server/services/confirmAnalysisService.ts| persistConfirmedVersionFile          |

8.2 Tokens

  Admin (R2_ADMIN_ACCESS_KEY_ID / R2_ADMIN_SECRET_ACCESS_KEY):
    - HeadBucket, CreateBucket em r2BucketProvisioner.ts
    - Chamado via ensureTenantBucket() antes de operações por tenant

  Runtime (R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY):
    - PutObject, GetObject, DeleteObject em r2StorageProvider.ts
    - Staging tmp/* também usa runtime client

  CLOUDFLARE_R2_ADMIN_API_TOKEN:
    - Presente no .env / env-check
    - NÃO usado no código de storage analisado (S3 API apenas)

8.3 Bucket naming

  Modo per_tenant (R2_BUCKET_MODE=per_tenant):
    doqyn-t-<sha256(tenantId).slice(0,12)>
    Exemplo determinístico: tenant "company_dev" -> hash fixo (ver testes r2-storage)

  Modo shared: R2_DEFAULT_BUCKET

  Sem PII no nome (r2BucketNaming.ts documentado e testado)

8.4 Object key

  Confirmado / versão:
    {R2_KEY_PREFIX}/{documentId}/versions/{versionId}/original.{ext}
    Default prefix: documents/...

  Staging:
    tmp/{jobId}/original.{ext}

  Extensão: sanitizeFileExtension (MIME ou ext validada, nunca nome original)

8.5 Provider R2 realmente usado?

  SIM quando STORAGE_PROVIDER=r2 e config.r2 presente:
    getStorageProvider() -> createR2StorageProvider()
  isStorageConfigured() usa isR2StorageConfigured() (exige credenciais admin+runtime)

8.6 Fallback local

  STORAGE_PROVIDER=local -> createLocalStorageProvider() explicitamente
  STORAGE_PROVIDER=r2 -> NÃO cai em local no getStorageProvider()
  Risco silencioso: se STORAGE_PROVIDER=r2 mas isR2StorageConfigured() false,
    isStorageConfigured() false -> staging skipped, storage pending no confirm
    (não grava em disco local sem perceber, mas também não grava no R2)

8.7 Original intacto

  PutObject envia buffer do staging sem transformação
  Nenhuma compressão/re-encode no pipeline confirmado
  Preview futuro deve ser objeto separado (não sobrescrever original)
