3. O ERRO SSL — O QUE SIGNIFICA
--------------------------------------------------------------------------------

Mensagem:
  400455F7C97F0000:error:0A000438:SSL routines:ssl3_read_bytes:
  tlsv1 alert internal error (SSL alert number 80)

Interpretação técnica:
  - O cliente Node.js (driver MongoDB) iniciou handshake TLS com o servidor
  - O servidor Atlas respondeu com "internal error" (alerta 80) e encerrou
  - Duração ~30s coincide com serverSelectionTimeoutMS padrão do driver

Causas frequentes em MongoDB Atlas + dev local:
  [A] IP atual não está na Network Access List do cluster
  [B] URI incorreta, cluster pausado/deletado ou credenciais inválidas
  [C] Proxy/firewall/VPN interceptando TLS
  [D] Incompatibilidade TLS/OpenSSL (menos comum em Node 20+)
  [E] Atlas em região bloqueada ou instabilidade temporária do cluster

NÃO é o padrão típico de:
  - Groq API (erro seria HTTP 4xx/5xx, não alert TLS OpenSSL puro)
  - Cloudflare R2 (SDK AWS retorna erro estruturado diferente; staging nem rodou)
  - auth-service (auth já passou antes do log no_ai)

5. O QUE É "RAG" NESTE PROJETO
--------------------------------------------------------------------------------

Arquivo: server/services/retrievalProvider.ts
Modo ativo: RETRIEVAL_MODE = 'hybrid' (constante)

Implementação: server/services/hybridChunkRetriever.ts
  - Chunking do texto extraído do PDF
  - Scoring por keywords/regex das regras de classe
  - Seleção top-K em memória
  - NÃO usa vector DB, FAISS, Atlas Vector Search nem Google Document AI

RAG só executa no modo groq (AI_MODE != no_ai), após extração de texto.

Com AI_MODE=no_ai:
  - NÃO há extração de texto do PDF
  - NÃO há chunking
  - NÃO há retrieval/RAG
  - NÃO há chamadas Groq

Portanto: o usuário pode estar associando "erro na hora do rag" ao fluxo de
análise em geral, mas neste log específico o RAG nem chegou a ser invocado.


6. POR QUE AI_MODE=no_ai NÃO RESOLVE O ERRO
--------------------------------------------------------------------------------

Expectativa comum (incorreta):
  "no_ai = tudo local, sem dependências externas"

Realidade no código:

  loadActiveDocumentClassRules() [modo groq]:
    - Se MONGODB_URI ausente -> fallback mock (DOCUMENT_CLASS_RULES)
    - Se MONGODB_URI presente -> MongoDB obrigatório

  getMongoClassAndRule() [modo no_ai]:
    - SEMPRE chama loadFromGovernanceCollections()
    - NÃO tem fallback mock
    - Exige classe class_confidentiality_agreement + rule_confidentiality_agreement_v1
      no Mongo do tenant company_dev

Assimetria importante:
  no_ai é MAIS dependente de MongoDB que groq quando URI está configurada
  mas Atlas está inacessível (groq poderia usar mock de regras; no_ai não).

Variáveis relacionadas:
  AI_MODE=no_ai          -> desliga LLM e RAG
  NO_AI_TEMPLATE=nda     -> template de metadados fixos
  MONGODB_URI=...        -> AINDA obrigatório para no_ai buscar classe/regra

12. CONCLUSÃO FINAL
--------------------------------------------------------------------------------

Pergunta: "O que pode estar dando errado no flow da IA?"

Resposta direta para ESTE log:
  1. Não é RAG — modo no_ai não executa retrieval.
  2. Não é Groq — LLM desligado por AI_MODE=no_ai.
  3. É MongoDB Atlas inacessível no passo getMongoClassAndRule, após o log
     informativo de no_ai, com timeout TLS ~30 segundos.

A variável AI_MODE=no_ai está funcionando (log confirma). O que permanece
quebrado é a dependência de governança documental no MongoDB, que o modo no_ai
ainda exige sem fallback mock.

Ação imediata recomendada:
  - Corrigir conectividade MONGODB_URI / Atlas Network Access
  - OU implementar fallback dev para no_ai quando Mongo indisponível
  - Rodar scripts/test-no-ai.mjs após Mongo OK para validar seed NDA
