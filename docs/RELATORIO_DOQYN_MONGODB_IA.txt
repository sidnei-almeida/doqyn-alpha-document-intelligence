1. VISAO GERAL DO PROJETO
================================================================================

O DOQYN e uma plataforma experimental de analise e governanca documental.
Nesta fase, o objetivo e validar o fluxo ponta a ponta com PDFs textuais
(texto selecionavel), sem OCR, sem storage externo e sem busca vetorial.

Capacidades implementadas no codigo:

  - Envio de PDF textual pelo frontend (tela /upload)
  - Extracao e normalizacao de texto no backend
  - Chunks temporarios em memoria + retriever hibrido
  - Analise com Groq (classificacao + extracao de metadados)
  - Geracao deterministica de nome recomendado no backend
  - Validacao de JSON da IA antes de persistir
  - Confirmacao de metadados pelo usuario
  - Persistencia no MongoDB Atlas (documents, versoes, jobs, auditoria)
  - Placeholders de storage AWS S3 / Cloudflare R2 (status pending)

Capacidades explicitamente FORA desta fase:

  - FAISS
  - MongoDB Atlas Vector Search
  - Embeddings persistentes
  - Collection document_chunks
  - Busca semantica global / chat documental
  - OCR, Google Document AI, upload real para S3/R2

Stack relevante:

  - Frontend : React + Vite + TypeScript
  - Backend  : API (pasta api/) + dev-server local (porta 3001)
  - IA       : Groq SDK (somente backend)
  - Retrieval: hibrido em memoria (server/services/hybridChunkRetriever.ts)
  - Banco    : MongoDB Atlas via driver nativo mongodb (^7.x)
  - Legado   : mongoose em modulos antigos (coexistencia; unificacao pendente)

2.2 Abordagem escolhida: Retriever hibrido em memoria
------------------------------------------------------
Arquivos responsaveis:

  - server/services/hybridChunkRetriever.ts  (scoring e selecao)
  - server/services/retrievalProvider.ts     (abstracao; modo "hybrid")
  - server/ai/services/documentChunker.ts    (criacao de chunks)
  - server/ai/constants.ts                 (RETRIEVAL_MODE = "hybrid")

O retriever pontua cada chunk por:

  - keywords das classes (document_classes / mock fallback)
  - nome e descricao da classe
  - aliases, labels e descricoes dos campos (document_rules)
  - regex de CNPJ
  - regex de datas (dd/mm/yyyy e yyyy-mm-dd)
  - regex de valores monetarios (R$)
  - regex de numero de nota fiscal e numero de pedido
  - termos juridicos/comerciais (contratante, contratada, vigencia, etc.)
  - frequencia de matches (ate 3 ocorrencias por termo)
  - diversidade de matches (bonus por variedade de termos)
  - proximidade de aliases a valores (: nº CNPJ valor)
  - bonus por posicao no documento (paginas 1-4)
  - penalizacao de chunks muito curtos
  - penalizacao por negativeKeywords da classe

Cada chunk selecionado retorna:

  - score          : pontuacao numerica
  - matchedTerms   : termos que contribuiram
  - reason         : justificativa textual curta do ranking
  - pageNumber     : pagina de origem
  - chunkIndex     : indice do trecho na pagina

2.3 Motivo da decisao
---------------------
O objetivo atual do DOQYN NAO e chat documental nem busca semantica global.
O objetivo e:

  1. Receber PDF textual
  2. Selecionar trechos relevantes por regras de negocio
  3. Enviar contexto reduzido para Groq
  4. Classificar dentro de classes cadastradas
  5. Extrair metadados conforme document_rules
  6. Gerar nome recomendado
  7. Persistir apenas o resultado final no MongoDB

Para isso, scoring deterministico em memoria e suficiente, testavel e seguro.

3. FLUXO ATUALIZADO DA ANALISE DOCUMENTAL
================================================================================

PDF textual
  -> upload no frontend (/upload)
  -> POST /api/ai/analyze-pdf (multipart, campo file)
  -> validacao de tipo/tamanho (PDF, max 15MB)
  -> extracao de texto (pdf-parse / PDFParse)
  -> normalizacao do texto (textNormalization.ts)
  -> divisao em chunks temporarios em memoria (documentChunker.ts)
  -> selecao de trechos pelo retriever hibrido (retrievalProvider.ts)
  -> envio dos trechos relevantes para Groq (classificador + extrator)
  -> classificacao restrita as classes cadastradas
  -> extracao restrita aos campos da regra ativa
  -> validacao de JSON no backend (validation.ts, documentValidators.ts)
  -> geracao de nome recomendado no backend (documentNaming.ts)
  -> retorno JSON + logs de negocio ao frontend
  -> usuario revisa e clica "Confirmar metadados"
  -> POST /api/documents/confirm-analysis (autenticado)
  -> persistencia em documents, document_versions, processing_jobs, audit_logs
  -> descarte automatico de chunks e texto bruto ao fim da request

Constantes de chunking/retrieval (server/ai/constants.ts):

  CHUNK_SIZE                    = 1800
  CHUNK_OVERLAP                 = 250
  MAX_CHUNKS_FOR_CLASSIFICATION = 8
  MAX_CHUNKS_FOR_EXTRACTION     = 10
  MAX_CHUNKS_PER_FIELD          = 4
  MIN_CLASSIFICATION_CONFIDENCE = 0.70
  MIN_FIELD_CONFIDENCE          = 0.60

4. CHUNKS TEMPORARIOS
================================================================================

Regras obrigatorias nesta etapa:

  - Chunks sao criados APENAS em memoria durante analyzePdfBuffer()
  - Chunks NAO sao salvos no MongoDB
  - Texto completo do PDF NAO e salvo no MongoDB
  - Chunks sao descartados ao final da requisicao HTTP de analise
  - Variaveis locais (extracted, chunks, classificationChunks, extractionChunks)
    sao coletadas pelo garbage collector apos a resposta

O que PODE ser salvo (somente apos confirmacao):

  - Evidencias curtas em document_versions.metadata[campo].evidence
  - Formato: { pageNumber?, snippet } com snippet limitado (~300 caracteres)
  - Nunca o chunk inteiro nem o texto integral do documento

Logs na UI (linguagem de negocio):
  "Trechos relevantes selecionados para analise."

Logs internos (backend, nivel debug):
  - quantidade total de chunks criados
  - topK selecionado para classificacao e extracao
  - scores por chunk
  - matchedTerms
  - via logger.debug + buildRetrievalStats()

7.3 Por que os dados apareceram em doqyn_alpha
----------------------------------------------
  Causa: o .env local tinha MONGODB_DB_NAME=doqyn_alpha sem MONGODB_DATABASE.
  O driver nativo antigo usava a cadeia:
    MONGODB_DATABASE || MONGODB_DB_NAME || doqyn_dev
  Como MONGODB_DATABASE estava ausente, o app gravava em doqyn_alpha.
  O mongoose legado usava env.MONGODB_DB_NAME com default doqyn_alpha.

7.4 Padronizacao aplicada (jun/2026)
------------------------------------
  Decisao: MONGODB_DATABASE e a unica variavel usada pelo app.
  Fallback hardcoded: doqyn_dev (server/db/database.ts)
  MONGODB_DB_NAME removido do codigo da aplicacao.
  /api/health retorna o nome real do database (nao apenas "configured").

  Acao recomendada no .env local:
    MONGODB_DATABASE=doqyn_dev
    Remover ou ignorar MONGODB_DB_NAME

  Dados historicos em doqyn_alpha permanecem no Atlas ate migracao manual.
  Apos padronizacao, npm run db:setup popula doqyn_dev com classes/regras.

7.5 Conexao no backend
----------------------
  Cliente nativo (fluxo novo):
    Arquivo  : server/db/mongoClient.ts

13. RETRIEVER HIBRIDO — DETALHES TECNICOS

13.1 Arquivos
-------------
  server/services/hybridChunkRetriever.ts   — implementacao do scoring
  server/services/retrievalProvider.ts      — facade; modo "hybrid" ativo
  server/ai/services/documentChunker.ts     — entrada: ExtractedPdfText
  server/ai/services/analyzePdfService.ts   — orquestrador do fluxo

Nota: caminho efetivo e server/services/ (nao server/src/services/).

13.2 Tipos
----------
  DocumentChunk:
    id, pageNumber?, chunkIndex, text, charStart?, charEnd?

  RetrievedChunk (extends DocumentChunk):
    score, matchedTerms[], reason

13.3 Funcoes principais
-----------------------
  retrieveChunksForClassification({ chunks, classes, topK? })
    -> top 8 chunks por score de classificacao

  retrieveChunksForExtraction({ chunks, selectedClass, topK? })
    -> merge por campo; top 10 chunks unicos

  retrieveChunksForField({ chunks, field, selectedClass, topK? })
    -> top 4 chunks por campo (usado internamente na extracao)

  formatChunksForPrompt(chunks)
    -> texto para Groq: [pagina N, trecho M] + conteudo

  buildRetrievalStats({ totalChunks, classificationChunks, extractionChunks })
    -> metricas internas para logger.debug

13.4 Diferenca classificacao vs extracao
----------------------------------------
  Classificacao:
    - Termos de TODAS as classes (keywords, nome, descricao)
    - negativeKeywords penalizam
    - Termos juridicos/comerciais genericos
    - topK = 8

  Extracao:
    - Termos por CAMPO (aliases, label, descricao)
    - Bonus de proximidade alias->valor
    - Padroes regex (CNPJ, data, valor, numero)
    - Merge dos melhores chunks por campo
    - topK = 10

13.5 UI vs logs internos
------------------------
  UI (logs de negocio):
    "Trechos relevantes selecionados para analise."

  UI NAO mostra:
    retriever, regex, scoring, chunks, Groq, MongoDB, backend

  Logs internos (JSON via logger):
    totalChunks, classificationTopK, extractionTopK, scores, matchedTerms

13.6 Modos futuros (retrievalProvider.ts)
-----------------------------------------
  RetrievalMode = "hybrid" | "faiss" | "atlas_vector" | "google"
