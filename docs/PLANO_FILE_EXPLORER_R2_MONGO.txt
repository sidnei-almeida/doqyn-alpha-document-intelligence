0. VISÃO E PRINCÍPIOS
================================================================================

Objetivo:
  Permitir que o usuário crie pastas, navegue em árvore, envie documentos para
  uma pasta, mova/renomeie arquivos e pastas, arquive/apague, com reflexo lógico
  no app e físico controlado no R2 — sem expor credenciais ao frontend.

Princípio central (NÃO NEGOCIÁVEL):
  MongoDB = fonte de verdade da árvore lógica e metadados.
  R2       = armazenamento físico de blobs (original, preview, assets).
  Frontend = nunca acessa R2; todo I/O passa pelo backend autenticado.

Decisão arquitetural crítica — duas camadas de path:

  CAMADA A — Storage canônico (existente, NÃO mudar em moves):
    {basePrefix}/documents/{documentId}/versions/{versionId}/original/{file}
    {basePrefix}/documents/{documentId}/versions/{versionId}/preview/...

    Definida em server/storage/storageKeys.ts (buildDocumentVersionObjectKey).
    objectKey gravado em MongoDocumentVersion.storage.primary/preview.
    Preview manifest, download, tracking e versionamento dependem desta chave.

  CAMADA B — Explorer lógico (nova, Mongo-first):
    Árvore de pastas em document_folders + folderId em documents.
    Moves/renames de arquivo na UI = atualização Mongo (folderId, displayName).
    NÃO reescrever objectKeys da Camada A ao mover entre pastas.

  CAMADA C — Espelho opcional R2 para pastas (fases posteriores):
    Placeholders de pasta vazia e, se necessário, índices por prefixo.
    Objetos físicos de documento permanecem na Camada A.

Por que não embutir folderPath no objectKey canônico:
  - Mover documento exigiria copy+delete de original + preview + pages + thumbs
  - previewManifest quebraria; versões antigas ficariam órfãs
  - Alto risco de inconsistência mid-copy
  - Contradiz restrição "não mover paths internos de preview"

Conclusão: File Explorer é primariamente um modelo LÓGICO em Mongo, com R2
refletindo pastas via placeholders e listagem por convenção — não via
reorganização dos blobs versionados.

1. MODELO DE DADOS MONGODB
================================================================================

1.1 Nova coleção: document_folders_{tenantPrefix}
--------------------------------------------------------------------------------

Tipo: MongoDocumentFolder

Campos propostos:

  _id                  string (UUID)           — folderId
  tenantId             string                  — tenant canônico
  companyId            string                  — compat legado
  tenantType           'business' | 'individual'
  ownerTenantId        string?                 — isolamento individual pool
  ownerUserId          string?                 — dono em tenant individual

  name                 string                  — nome exibido (único entre irmãos)
  slug                 string                  — derivado de name (sanitizado)
  parentFolderId       string | null           — null = raiz do explorer do tenant
  ancestorIds          string[]                — materialized path para queries
  depth                number                  — 0 = raiz

  /** Caminho lógico estável para R2 placeholder e auditoria (não é objectKey de doc) */
  logicalPath          string                  — ex: /Contratos/2026/Fornecedores
  r2PlaceholderKey     string | null           — chave do marker .folder no R2

  /** Vínculo opcional com governança (NÃO substitui classId do documento) */
  linkedCategoryId     string | null           — document_categories._id se pasta espelha categoria

  status               'active' | 'archived'
  deletedAt            Date | null             — soft delete

  createdBy            string                  — userId
  createdAt            Date
  updatedAt            Date
  updatedBy            string?

Índices:

  UNIQUE (tenantId, parentFolderId, slug, deletedAt)  — nomes únicos por nível
  INDEX  (tenantId, parentFolderId, status, deletedAt)
  INDEX  (tenantId, ancestorIds)
  INDEX  (tenantId, ownerUserId)                      — individual pool
  INDEX  (tenantId, linkedCategoryId)                 — sync opcional com categorias

Regras de negócio:
  - Profundidade máxima sugerida: 20 níveis (configurável)
  - Nome: 1–120 chars; proibir / \ .. NUL; normalizar espaços
  - slug: slugify(name); em conflito, sufixo -2, -3...
  - Não permitir ciclos em parentFolderId (validar ancestorIds)
  - Soft delete em pasta: exige pasta vazia (sem subpastas ativas nem docs ativos)

1.2 Alteração em documents_{tenantPrefix} (MongoDocument)
--------------------------------------------------------------------------------

Campos novos (aditivos — não quebrar docs existentes):

  folderId             string | null           — null = "Biblioteca raiz" / sem pasta manual
  folderPath           string | null           — denormalizado: logicalPath da pasta (cache)
  displayName          string?                 — nome amigável na pasta (default: currentFileName)

Campos existentes preservados:
  classId, className     — classificação IA / governança (ORTOGONAL a folderId)
  currentFileName        — nome técnico da versão atual
  status, processingStatus
  storage via versions   — inalterado

Migração inicial:
  - folderId = null para todos os documentos existentes
  - Documentos continuam visíveis na raiz do File Explorer
  - Espaços atuais (?space=categoryId) permanecem como filtro de governança

1.3 Relação folderId vs classId (categoria / espaço)
--------------------------------------------------------------------------------

Conceitos distintos:

  classId / categoryId  → governança, regras IA, extração, permissões de grupo
  folderId              → organização do usuário estilo file manager

Um documento pode estar em:
  - Pasta "Contratos/2026" (folderId)
  - Classificado como "Nota Fiscal" (classId)

A Biblioteca atual usa classId como "espaço". O File Explorer adiciona
hierarquia manual. Convivência planejada:

  - Modo navegação: ?folder={folderId} (novo) vs ?space={categoryId} (atual)
  - Filtros combináveis: folderId + categoryId + search + status
  - Upload pode especificar folderId de destino; classId continua vindo da IA

1.4 Soft delete e lixeira
--------------------------------------------------------------------------------

  Documento arquivado: status='archived' (já existe) — permanece com folderId
  Pasta arquivada: status='archived' + deletedAt — filhos devem estar vazios ou movidos
  Restaurar: limpar deletedAt / status active

Lixeira da Biblioteca (collection lixeira) continua filtrando status archived;
File Explorer pode mostrar pastas arquivadas em view separada (fase posterior).

1.5 Preparação para permissões por pasta (fase 6 — só modelo)
--------------------------------------------------------------------------------

Campos reservados em document_folders (nullable na fase 1):

  inheritPermissions   boolean  default true
  accessGroupIds       string[] default []   — vazio = herda tenant default

Em documents (fase 6):
  folderAccessOverride  null | { viewGroupIds, ... }

Não implementar enforcement na fase 1–5; apenas schema e tipos TypeScript.

2. ESTRATÉGIA R2 (Cloudflare R2 / S3-compatible)
================================================================================

2.1 O que NÃO fazer no R2
--------------------------------------------------------------------------------

  - Não colocar R2 API token no frontend ou em VITE_*
  - Não usar ListObjects do browser
  - Não mover/renomear objectKeys em documents/{documentId}/versions/... ao mover pasta
  - Não deletar blobs de preview ao mover documento entre pastas
  - Não usar R2 como única fonte da árvore

2.2 Padrão de prefixos propostos
--------------------------------------------------------------------------------

Manter Camada A intacta:

  Business:
    documents/{documentId}/versions/{versionId}/original/{storageFileName}
    documents/{documentId}/versions/{versionId}/preview/...

  Individual (+ basePrefix opaco):
    individuals/{hash16}/documents/{documentId}/versions/...

Nova Camada C — markers de pasta (placeholders):

  {basePrefix}/explorer/folders/{folderId}/.folder

  Conteúdo: JSON mínimo (opcional) ou zero-byte:
    { "folderId", "tenantId", "logicalPath", "createdAt" }
  Content-Type: application/x-doqyn-folder ou application/octet-stream

Prefixo lógico para listagem administrativa (opcional, fase 2):

  {basePrefix}/explorer/by-path/{encodedLogicalPath}/.folder

  encodedLogicalPath = segmentos URL-safe, sem ..

NÃO criar:
  explorer/by-path/.../arquivo.pdf como cópia do original (evitar duplicação)

2.3 Criar placeholder de pasta
--------------------------------------------------------------------------------

Fluxo POST /api/file-explorer/folders:

  1. Validar tenant + nome + parent
  2. Inserir document_folders no Mongo
  3. Se storage configurado:
       PUT r2PlaceholderKey com body vazio ou metadata JSON
  4. Atualizar folder.r2PlaceholderKey
  5. Audit: folder.created

Idempotência: se PUT falhar após insert Mongo, job de reconciliação recria marker;
pasta continua listável via Mongo mesmo sem marker R2.

2.4 Listar por prefix/delimiter (uso limitado)
--------------------------------------------------------------------------------

ListObjectsV2 com:
  Prefix: {basePrefix}/explorer/folders/{parentFolderId}/
  Delimiter: /

Uso previsto:
  - Auditoria / scripts de consistência Mongo↔R2
  - NÃO como API principal do frontend (frontend usa GET /api/file-explorer/items)

A listagem do usuário vem do Mongo (rápida, permissões, metadados).

2.5 Mover arquivo — estratégia segura
--------------------------------------------------------------------------------

FASE 3–4 (recomendada): MOVE LÓGICO APENAS

  PATCH /api/file-explorer/items/:documentId/move { folderId }
    1. Validar documento no tenant + permissão canEditMetadata ou nova canMoveDocument
    2. Validar folderId destino (existe, active, mesmo tenant)
    3. Atualizar documents.folderId + folderPath (denormalizado)
    4. Audit: document.moved { fromFolderId, toFolderId }
    5. ZERO operações R2 na Camada A

Justificativa: objectKey não contém folderPath; mover no R2 não altera semântica
para o app e introduz risco sem benefício.

FASE 4 alternativa (somente se exigência explícita de espelho físico):

  Manter ponteiro simbólico (NÃO cópia do PDF):
    {basePrefix}/explorer/index/{folderId}/{documentId} → objeto 0-byte com
    { "canonicalKey": "documents/.../original/..." }

  Copy+delete do PDF completo + preview: PROIBIDO na v1 por risco a versionamento.

2.6 Renomear pasta
--------------------------------------------------------------------------------

  PATCH /api/file-explorer/folders/:id { name }
    1. Atualizar name, slug, logicalPath em Mongo (e descendentes em batch)
    2. R2: criar novo placeholder .folder no path novo; deletar marker antigo
    3. NÃO mover objetos documents/{documentId}/...
    4. Audit: folder.renamed

Renomear pasta com muitos descendentes: atualizar logicalPath em subpastas via
ancestorIds (job assíncrono se > 500 nós).

2.7 Renomear arquivo (documento)
--------------------------------------------------------------------------------

  PATCH /api/file-explorer/items/:id/rename { displayName }
    1. Atualizar documents.displayName e, se política permitir, currentFileName
    2. Opcional: nova versão com filename_updated (já existe audit document.filename_updated)
    3. NÃO renomear storageFileName/objectKey da versão atual salva
       (quebraria integridade; nova versão futura pode gerar novo storageFileName)

Distinção:
  - displayName: rótulo na pasta (explorer)
  - currentFileName / storageFileName: pipeline de versão (inalterado no rename simples)

2.8 Upload para pasta
--------------------------------------------------------------------------------

  Camada A inalterada: após confirm-analysis, storeUploadedDocumentFile usa
  documentId/versionId — independente de folderId.

  Mongo: ao criar documento em confirmAnalysisPersistence, aceitar folderId opcional
  no payload e gravar em documents.folderId.

  R2: não adicionar folderId ao objectKey.

2.9 Evitar quebra de preview / versionamento
--------------------------------------------------------------------------------

Regras:
  - previewManifest referencia objectKeys da versão; imutáveis após geração
  - generateDocumentPreviewForVersion lê primary.objectKey — nunca derivar de folder
  - Download/preview APIs: resolvem por documentId + versionId, não por folder path
  - Tracking events: documentId permanece estável ao mover pasta

Teste de regressão obrigatório em cada fase:
  upload → confirm → preview → download → move folder → preview/download novamente

2.10 Reconciliação Mongo ↔ R2
--------------------------------------------------------------------------------

Script seguro (fase 2+): npm run audit:explorer-r2-consistency
  - Pastas Mongo sem .folder marker → reportar / recriar
  - Markers R2 órfãos (sem Mongo) → reportar (não auto-delete)
  - Nunca comparar contagem de objetos documents/ com contagem de docs Mongo
    (previews multiplicam objetos)

3. ENDPOINTS BACKEND

Namespace: /api/file-explorer

3.1 GET /api/file-explorer/items
--------------------------------------------------------------------------------

Query:
  folderId     string | 'root'   — pasta atual (default root)
  categoryId   string?           — filtro opcional classId (governança)
  search       string?
  status       string?
  cursor       string?
  limit        number (max 100)
  include      'folders' | 'documents' | 'all' (default all)

Response:
{
  "folder": { "id", "name", "parentFolderId", "logicalPath", "breadcrumb": [...] },
  "folders": [{ "id", "name", "slug", "childFolderCount", "documentCount", "updatedAt" }],
  "documents": [{ ...DocumentListItem, "folderId", "displayName" }],
  "pagination": { "nextCursor" }
}

Implementação:
  - Pastas: query document_folders by parentFolderId
  - Docs: listDocuments + filter folderId
  - Contagens: aggregation ou cache (evitar N+1)

3.2 POST /api/file-explorer/folders
--------------------------------------------------------------------------------

Body: { name, parentFolderId?: null | string, linkedCategoryId?: string }
Response 201: { folder: MongoDocumentFolder }
Erros: 409 NAME_CONFLICT, 400 INVALID_PARENT, 403 FORBIDDEN

3.3 PATCH /api/file-explorer/folders/:id
--------------------------------------------------------------------------------

Body: { name?, parentFolderId? (move folder), status? }
Move pasta: validar não mover para descendente; atualizar ancestorIds em subtree

3.5 PATCH /api/file-explorer/items/:documentId/move

3.6 PATCH /api/file-explorer/items/:documentId/rename

3.7 POST /api/file-explorer/upload

    Frontend usa fila existente com UploadContext.folderId

  Opção B: multipart proxy — evitar; manter analyze-pdf existente

Integração real:

6.1 Tenant isolation
--------------------------------------------------------------------------------

  - Todas as queries com tenantScopeFilterFromContext(storage)

--------------------------------------------------------------------------------

  Listar: canUserListDocument (existente)
  Criar pasta: canConfirmDocuments ou novo canManageFolders (admin/editor)

--------------------------------------------------------------------------------

  - logicalPath: rejeitar .., //, \, caracteres de controle
  - slug: slugifyName existente
  - folderId: assertSafeStorageSegment ao montar r2PlaceholderKey
  - Nunca aceitar logicalPath do cliente como chave R2 direta — só server-side

6.4 Sanitização de nomes
--------------------------------------------------------------------------------

  Reutilizar shared/storageFileName.ts e slugify.ts
  Nomes de pasta: mais permissivos que storageFileName (espaços, acentos)
  Proibir: / \ : * ? " < > | e leading/trailing dots

6.5 Não expor objectKey
--------------------------------------------------------------------------------

  APIs retornam: canPreview, canDownload, documentId, versionId
  Preview/download: endpoints existentes /api/documents/:id/preview
  Nunca retornar storage.primary.objectKey ao frontend

7. RISCOS E MITIGAÇÕES
================================================================================

Risco                              | Impacto | Mitigação
-----------------------------------|---------|----------------------------------
Mover objeto R2 canonical          | Crítico | Move só Mongo; não tocar Camada A
Inconsistência Mongo/R2 markers  | Médio   | Mongo autoritativo; job reconciliação
Falha mid copy/delete            | Alto    | Evitar copy/delete de PDFs; transação Mongo
Preview quebrado após move       | Alto    | objectKey imutável; testes E2E
Versões antigas órfãs            | Alto    | Não renomear keys por versão salva
Performance listagem árvore      | Médio   | ancestorIds, paginação, cache counts
Conflito nome irmão              | Baixo   | UNIQUE slug+parent; 409 claro
Confusão folder vs category      | Médio   | UI distinta; docs; campos separados
Upload sem fix prévio            | Crítico | Gate: corrigir BUG-001 antes fase 3
Duplicar upload endpoint         | Médio   | Reusar analyze/confirm + folderId
