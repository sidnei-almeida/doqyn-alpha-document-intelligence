2. DOCUMENT VIEWER — PERSISTÊNCIA DO previewManifest
================================================================================

PROBLEMA
--------
O manifest era montado em runtime a cada request. Para PDF, o backend extraía
dimensões do PDF watermarkado via pdf-lib — custoso e repetitivo.

SOLUÇÃO
-------
Campo version.previewManifest persistido em MongoDocumentVersion.

FLUXO
-----
1. Após generateDocumentPreviewForVersion (PDF):
   - extractPdfPageDimensions no buffer watermarkado
   - Monta MongoPreviewManifest (viewerType: pdf_pages, source: preview_pdf)
   - Retorna { slot, previewManifest }

2. confirmAnalysisService grava previewManifest no insert da versão

3. getDocumentPreviewManifest:
   - Prioriza previewManifest salvo (ensurePdfPreviewManifest)
   - Se ausente: gera sob demanda, persiste e retorna

ARQUIVOS
--------
- server/preview/previewManifestPersistence.ts (novo)
- server/services/documentPreviewService.ts (retorno estendido)
- server/services/documentPreviewManifestService.ts (ensure + cache)
- server/db/types.ts (MongoPreviewManifest enriquecido)
- server/services/confirmAnalysisService.ts (grava manifest na versão)

3. DOCUMENT VIEWER — CACHE DE PÁGINAS PDF EM STORAGE
================================================================================

ESTRATÉGIA: Opção A — cache em storage (implementada)

FLUXO
-----
1. GET /preview/pages/{n} ou /preview/thumbnails/{n}
2. Se previewObjectKey/thumbnailObjectKey existir no manifest → lê do storage
3. Senão: renderiza via Ghostscript do PDF watermarkado → salva PNG → atualiza Mongo

PATHS DE STORAGE
----------------
- preview/pages/page-{n}.png
- preview/thumbnails/thumb-page-{n}.png

FUNÇÕES
-------
- buildDocumentPreviewPageAssetObjectKey (storageKeys.ts)
- storePreviewAsset / persistPreviewAsset (storage providers)
- readCachedPageAsset / cacheRenderedPage (manifest service)
- updatePreviewManifestPageCache (previewManifestPersistence.ts)

REGRAS
------
- Páginas sempre do preview PDF watermarkado, nunca do original
- objectKey interno — nunca retornado na API pública
- Cache-Control continua private, no-store na resposta HTTP

4. DOCUMENT VIEWER — PIPELINE DE PREVIEW PARA IMAGENS
================================================================================

DEPENDÊNCIA NOVA
----------------
- sharp (^0.34.x)

TIPOS SUPORTADOS
----------------
- image/jpeg
- image/png
- image/webp

FLUXO
-----
1. generateDocumentPreviewForVersion detecta MIME de imagem
2. generateWatermarkedImagePreviews (imagePreviewGenerator.ts):
   - Watermark DOQYN via SVG composite
   - Resoluções: thumbnail (320), small (720), medium (1440), large (2400)
3. Cada resolução salva em storage: preview/images/{label}.{ext}
4. previewManifest com viewerType: image, source: preview_image
5. GET /preview/image?size=small|medium|large resolve resolução correta

STORAGE KEYS
------------
- Originais: assertSafeOriginalStorageFileName (.pdf, .png, .jpg, .webp)
- buildDocumentPreviewImageResolutionObjectKey

FRONTEND
--------
- ImageViewer usa medium por padrão, large quando zoom > 1.25
- Manifest image com resolutions[] e URLs autenticadas

NOTA
----
confirm-analysis ainda envia contentType: application/pdf.
O pipeline de imagem no backend está pronto; conectar no fluxo analyze/confirm
para upload de imagens é próximo passo natural.
