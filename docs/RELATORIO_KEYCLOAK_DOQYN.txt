2. RESUMO EXECUTIVO
================================================================================

O que é o Keycloak dentro do DOQYN
----------------------------------
O Keycloak é o provedor de identidade (IdP) do DOQYN. Ele centraliza login,
senha, emissão de tokens JWT, sessão do usuário e atribuição de roles globais
da plataforma (doqyn_admin, company_admin, user). O aplicativo DOQYN não
armazena senhas de usuários finais no MongoDB.

Por que foi escolhido
---------------------
- Padrão de mercado para SSO e OpenID Connect.
- Suporte nativo a Authorization Code + PKCE para SPAs.
- Gestão de usuários, roles e políticas de senha sem reinventar autenticação.
- Permite separar identidade (Keycloak) de autorização de negócio (MongoDB).

   - Volume Docker para persistência

   - Imagem: quay.io/keycloak/keycloak:26.6.3

   - Depende do healthcheck do Postgres antes de iniciar

Modo start-dev
--------------
O Keycloak está rodando com "start-dev". Esse modo é adequado para:
  - Desenvolvimento inicial
  - Homologação controlada com acesso restrito

NÃO é recomendado para produção final porque:
  - Não representa hardening completo de produção
  - Configurações de cache, proxy e TLS precisam ser revisadas
  - Deve ser substituído por "start" (ou equivalente) com variáveis de proxy/HTTPS

Persistência
------------
O banco Postgres do Keycloak usa volume Docker. Os dados de realms, clients e
usuários sobrevivem a reinícios de container, mas ainda dependem de estratégia
de backup externa.

9. ROLES CRIADAS NO REALM DOQYN
================================================================================

doqyn_admin
  Administrador geral da plataforma DOQYN. Pode gerenciar configurações
  globais, clientes, usuários e recursos sistêmicos em qualquer tenant.

company_admin
  Administrador de um cliente/empresa (tenant business) ou contexto equivalente.
  Gerencia usuários, grupos, classes documentais e regras dentro do seu escopo.

user
  Usuário padrão. Acessa, envia, processa e visualiza documentos conforme
  permissões e grupos de acesso definidos no MongoDB.

Decisão arquitetural sobre roles
--------------------------------
- Essas roles são GLOBAIS e ficam no Keycloak (realm roles).
- Permissões finas (jurídico, financeiro, RH, diretoria, compras etc.) ficam
  no MongoDB em accessGroupIds / grupos de acesso.
- NÃO criar grupos Keycloak para cada área documental neste momento.
- O backend sincroniza apenas roles globais com o Keycloak; grupos documentais
  são exclusivamente MongoDB.

================================================================================
13. LÓGICA DE AUTENTICAÇÃO
================================================================================

Fluxo implementado / planejado (código do projeto)
--------------------------------------------------

  1. Usuário acessa o DOQYN (frontend Vite).
  2. Se VITE_AUTH_PROVIDER=keycloak, o frontend inicializa keycloak-js com PKCE.
  3. Usuário é redirecionado para a tela de login do Keycloak (realm doqyn).
  4. Após autenticação, Keycloak retorna access token ao frontend.
  5. Frontend mantém token em memória e anexa em cada requisição:
       Authorization: Bearer <token>
  6. Backend (requireAuth) lê o Bearer token.
  7. Backend valida assinatura JWT via JWKS:
       {KEYCLOAK_BASE_URL}/realms/{KEYCLOAK_REALM}/protocol/openid-connect/certs
  8. Backend valida issuer e audience/azp do client doqyn-web.
  9. Backend extrai sub, email, username e realm_access.roles do token.
 10. Backend localiza membership ativo em tenant_members (fallback: company_members).
 11. Backend carrega tenant em tenants e monta contexto completo.
 12. GET /api/me retorna user + tenant + membership.
 13. Se não houver vínculo ativo: HTTP 403
       "Seu usuário ainda não está vinculado a um cliente ativo no DOQYN."

Arquivos principais no repositório
----------------------------------
  Frontend:
    src/auth/keycloakClient.ts       -> init PKCE, token em memória
    src/auth/AuthProvider.tsx        -> contexto de autenticação
    src/auth/apiAuth.ts              -> authFetch com Bearer

  Backend:
    server/auth/keycloakJwtVerifier.ts  -> validação JWT (jose + JWKS)
    server/auth/requireAuth.ts          -> middleware Bearer/cookie
    server/auth/keycloakAdminService.ts -> Admin API (client credentials)
    api/me.ts                           -> contexto autenticado
    server/services/meService.ts        -> resolução user/tenant/membership

14. SEPARAÇÃO DE RESPONSABILIDADES
================================================================================

Keycloak é responsável por:
  - Identidade do usuário (sub, email, username)
  - Login e logout
  - Senha e políticas de credencial
  - Emissão e renovação de tokens JWT
  - Sessão OIDC
  - Roles globais: doqyn_admin, company_admin, user

MongoDB é responsável por:
  - Cliente/tenant (CPF ou CNPJ)
  - Vínculo usuário <-> tenant (tenant_members)
  - Status: pending, active, blocked, rejected
  - Aprovação, convite, bloqueio
  - Grupos de acesso documentais (accessGroupIds)
  - Permissões por classe documental
  - Classes e regras de documentos
  - Auditoria de ações administrativas e documentais
  - Resolução de collections por tenant (tenantResolver)
  - Isolamento CPF (pool compartilhado) vs CNPJ (prefixo de collection)

Regra de ouro
-------------
O frontend NUNCA chama a API administrativa do Keycloak.
Apenas o backend usa credenciais do client doqyn-admin-api.

15. DECISÃO ARQUITETURAL SOBRE TENANTS
================================================================================

O conceito central deixa de ser apenas "empresa" e passa a ser "tenant/cliente".

Tipos de tenant
---------------
  individual  -> Pessoa Física (CPF)
  business    -> Pessoa Jurídica (CNPJ)

Regras de isolamento
--------------------
  CPF (individual):
    - strategy: shared_individual_pool
    - Collections compartilhadas com prefixo "individual_pool"
    - Partição lógica obrigatória por tenantId e ownerUserId em cada documento

  CNPJ (business):
    - strategy: collection_prefix
    - Cada tenant tem prefixo interno único (ex.: company_dev, tenant_pj_xxx)
    - Collections físicas separadas por cliente

Fluxo de descoberta do tenant
------------------------------
  - Na criação de conta ou solicitação de acesso, o usuário informa CPF/CNPJ
    e dados do cliente.
  - Após login, o app descobre o tenant pelo vínculo em tenant_members.
  - O frontend NÃO escolhe collection.
  - O backend resolve collections via getTenantCollections(tenantId).

Compatibilidade legada
----------------------
  - companyId ainda existe como alias temporário de tenantId.
  - company_members ainda funciona como fallback durante migração.
  - DEV_TENANT_ID padrão: company_dev

19. FLUXOS DE USUÁRIO
================================================================================

Fluxo A: Primeiro admin de um cliente CNPJ
------------------------------------------
  1. doqyn_admin cria tenant business (tenants) com CNPJ.
  2. doqyn_admin cria ou aprova primeiro company_admin.
  3. Backend cria usuário no Keycloak (se não existir).
  4. Backend cria tenant_member ativo no MongoDB.
  5. Roles globais sincronizadas no Keycloak; grupos ficam no MongoDB.

Fluxo B: Usuário solicita acesso (público)
------------------------------------------
  Endpoint: POST /api/auth/access-requests
  1. Usuário informa dados + companyId/tenant (evolução: CPF/CNPJ).
  2. Sistema valida tenant ativo.
  3. Cria tenant_member com status "pending".
  4. NÃO cria usuário ativo no Keycloak ainda.
  5. Admin aprova posteriormente.

Fluxo C: Admin convida usuário
------------------------------
  Endpoint: POST /api/company-members/invite
  1. company_admin ou doqyn_admin envia convite.
  2. Backend cria usuário no Keycloak (enabled=true).
  3. Backend define senha temporária (dev) ou e-mail de ação (prod).
  4. Cria tenant_member ativo com roles e accessGroupIds.
  5. Sincroniza realm roles no Keycloak.

Fluxo D: Aprovação de solicitação pendente
------------------------------------------
  Endpoint: POST /api/company-members/:memberId/approve
  1. Verifica status pending.
  2. Cria/ativa usuário no Keycloak.
  3. Atualiza tenant_member para active.
  4. Atribui roles globais e grupos de acesso.

Fluxo E: Bloqueio
-----------------
  Endpoint: POST /api/company-members/:memberId/block
  1. MongoDB: status "blocked".
  2. Keycloak: usuário desabilitado (se keycloakUserId existir).
  3. Auditoria registrada.
  4. Preferir desativar em vez de deletar usuário no Keycloak.

Fluxo F: Reativação
-------------------
  Endpoint: POST /api/company-members/:memberId/activate
  1. MongoDB: status "active".
  2. Keycloak: usuário habilitado novamente.

25. CONCLUSÃO
================================================================================

O Keycloak já está funcional na VPS como provedor de autenticação inicial do
DOQYN. O realm doqyn, o client público doqyn-web, as roles globais e o usuário
de teste sidnei estão operacionais com acesso via túnel SSH.

No repositório do projeto, a integração avançou significativamente: o backend
valida JWT, expõe /api/me, possui serviço administrativo Keycloak, modelos
multi-tenant (tenants/tenant_members), resolução de collections por cliente e
endpoints de gestão de usuários. O frontend já suporta login Keycloak com PKCE
e envio de Bearer token.

Ainda é necessário fechar o ciclo operacional:
  - Criar o client doqyn-admin-api na VPS e configurar o segredo no backend.
  - Vincular usuários Keycloak a tenant_members no MongoDB.
  - Fazer o frontend depender de /api/me em vez de dados hardcoded.
  - Expor o Keycloak com HTTPS em domínio próprio.
  - Sair do modo start-dev e configurar SMTP/backup.

Com esses passos, o DOQYN terá autenticação corporativa real integrada ao modelo
multi-tenant (CPF/CNPJ), com governança por cliente, aprovação de usuários e
isolamento correto de dados documentais.
