DIVERGÊNCIAS EXPLÍCITAS COM O RELATÓRIO ORIGINAL
================================================================================

1. O relatório afirma [OK] "Frontend com keycloak-js, PKCE, token em memória"
   e lista separadamente [PENDENTE] consumo de /api/me — correto no pendente,
   mas o resumo executivo pode sugerir integração completa. Na prática a
   integração Keycloak→backend→tenant está INCOMPLETA no frontend.

2. O relatório afirma [OK] "Coleções tenants e tenant_members". No código,
   tenant_members é usada principalmente para LEITURA; persistência de membros
   ainda é company_members.

3. O relatório marca [OK] "Serviço administrativo Keycloak" sem distinguir que
   o código existe mas a operação depende de client não verificado na VPS.

4. authApi.meRequest espera resposta { user: AuthUser }, enquanto /api/me
   retorna envelope expandido. O campo legacyUser existe, mas meRequest lê
   data.user que no novo formato pode não ser AuthUser completo — risco PARCIAL
   no modo temporary se /api/me mudou formato (verificar em runtime).

5. requireAuth converte falha de membership (403 MEMBER_NOT_LINKED) em 401
   INVALID_BEARER_TOKEN — comportamento diferente do documentado no relatório.
