1. RESUMO EXECUTIVO
================================================================================

A refatoração transformou o app em workspace estilo Google Drive (/biblioteca) com
upload transversal (+ Novo → UploadQueueProvider → ReviewDrawer). O backend de
análise, confirmação, Mongo e R2 NÃO foi alterado na working tree — os endpoints
/api/ai/analyze-pdf e /api/documents/confirm-analysis permanecem os mesmos.

Os sintomas relatados (IA “travada”, documentos não aparecendo) são explicados por
uma combinação de:

  A) BUG CONFIRMADO NO FRONTEND (crítico): race condition no useEffect do
     UploadQueueProvider que cancela a chamada analyzePdf assim que o item entra
     em status "analyzing", deixando o item permanentemente em "Analisando com IA…"
     sem nunca receber resposta nem abrir revisão.

  B) FLUXO DE GOVERNANÇA INTENCIONAL MAS MAL COMUNICADO: auto-confirmação desligada
     por padrão (VITE_UPLOAD_AUTO_CONFIRM_ENABLED=false, autoReviewEnabled=false).
     Após análise bem-sucedida, o fluxo normal é pausar em "Aguardando revisão" e
     exigir ReviewDrawer + checkbox + Confirmar — se o usuário fecha o drawer ou
     não percebe a fila no canto, parece que “travou”.

  C) CONFIRMAÇÃO PODE FALHAR NO BACKEND (contrato): respostas de análise com
     status requires_review frequentemente trazem extraction: null; o schema Zod
     de confirm-analysis exige extraction como objeto — confirm retorna 400
     INVALID_PAYLOAD.

  D) LISTAGEM VAZIA — CAUSAS PLAUSÍVEIS APÓS CONFIRM BEM-SUCEDIDO:
     - Filtro ?space= (categoria) aplicado na raiz da Biblioteca enquanto o
       documento foi salvo com classId da IA (UploadContext.categoryId não é usado).
     - Filtro de status "Processado" no UI filtra status=processed, mas documentos
       confirmados são salvos com status=active (processingStatus=processed).
     - Coleções "Compartilhados", "Favoritos", "Lixeira" recortam a listagem.
     - Permissões de grupo (canUserListDocument) no backend.

  E) CONTEXTO DE UPLOAD DESCONECTADO: categoryId do espaço aberto é gravado em
     UploadQueueItem.context mas NUNCA é enviado a analyzePdf nem confirmAnalysis.

Veredicto geral: o problema é predominantemente FRONTEND/INTEGRAÇÃO (fila nova
incompleta e com bug de concorrência), com riscos de contrato backend já existentes
(extraction obrigatório) que o fluxo antigo também herdava em cenários de revisão.

5. POR QUE A ANÁLISE DA IA PARECE TRAVADA
================================================================================

CAUSA RAIZ CONFIRMADA (frontend):

Arquivo: src/features/upload/UploadQueueProvider.tsx
Linhas ~164-223: useEffect processa fila com dependência [items, ...].

Sequência do bug:
  1. Item queued → effect dispara analyzePdf async
  2. dispatch({ type:'status', status:'analyzing' }) atualiza items
  3. Effect reexecuta por mudança em items
  4. Cleanup do effect anterior: cancelled = true
  5. hasActiveItem(items) === true → effect retorna sem nova análise
  6. Promise analyzePdf resolve com cancelled===true → return silencioso
  7. Item permanece status:'analyzing' PARA SEMPRE

Evidência no código:
  - hasActiveItem só considera 'analyzing' | 'confirming' (uploadQueueState.ts:66-68)
  - Não há timeout, retry automático nem transição analyzing→error
  - UploadQueueDrawer mostra "Analisando com IA…" indefinidamente

Comparação: useBulkUploadQueue (fluxo antigo) usa refs, isolamento de requests
(bulkQueueIsolation.ts) e NÃO sofre este padrão de cleanup ao mudar status.

CAUSAS SECUNDÁRIAS (comportamento esperado mal percebido):

  a) Default reviewSettings.autoReviewEnabled = false
  b) VITE_UPLOAD_AUTO_CONFIRM_ENABLED default false (uploadAutoConfirm.ts)
  c) shouldPauseForReview default true para baixa confiança / campos ausentes
  d) Após análise OK → status 'review' + ReviewDrawer; fechar drawer deixa item
     em review sem bloquear fila — usuário precisa clicar "Revisar" no drawer
     inferior (UploadQueueDrawer)

  e) analyzePdf no novo fluxo passa só { context: { fileName } } — sem itemId/
     requestId explícitos (menor impacto; requestId é gerado no serviço)

Backend: endpoint /api/ai/analyze-pdf intacto. Se a requisição HTTP completasse,
retornaria status completed | requires_review | ai_unavailable | failed.
O travamento observado é frontend antes/depois da resposta.

  [C] confirm ok, Mongo ok, primary pending → doc listado mas sem preview/download
  [D] Mongo referencia objectKey errado → listagem ok, preview falha

Refatoração NÃO alterou adapters de storage no backend. Risco é indireto:
se confirm não é chamado, R2 fica só com staging temporário.

24. CONCLUSÃO
================================================================================

A refatoração da Biblioteca desconectou o fluxo de upload da navegação antiga
e introduziu uma nova orquestração (UploadQueueProvider) que REUTILIZA os
endpoints corretos, mas contém um bug crítico de concorrência que impede a
conclusão da análise na maioria dos casos — isso explica diretamente a percepção
de "IA travada" e a ausência de documentos na listagem (confirm nunca roda).

Mesmo com analyze funcionando, o fluxo padrão exige revisão manual no ReviewDrawer
(auto-confirm desligado) e o contexto de categoria do espaço aberto não afeta
a persistência — documentos podem ser salvos mas filtrados fora da vista atual.

O backend de persistência (Mongo, R2 staging→promote, preview, audit) permanece
coerente e não foi a causa primária da regressão; falhas adicionais vêm de
contrato extraction obrigatório e governança CLASS_OR_RULE_NOT_FOUND em alguns
tenants.

Prioridade de correção: (1) bug do useEffect na fila, (2) validação/contrato
confirm, (3) visibilidade na Biblioteca (filtros + contexto), (4) paridade com
/upload legado e invalidação de cache.
