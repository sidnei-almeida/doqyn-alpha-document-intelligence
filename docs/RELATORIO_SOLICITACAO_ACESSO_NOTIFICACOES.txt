3. ENDPOINTS
================================================================================

POST /api/auth/access-requests (público, sem login)
  - Cria/loca tenant por CPF/CNPJ (taxIdHash)
  - Cria tenant_member status pending
  - Cria usuário Keycloak (enabled, role user, senha temporária em dev)
  - Audit USER_ACCESS_REQUESTED, KEYCLOAK_USER_CREATED

GET /api/company-members (autenticado, admin)
  - Lista tenant_members via listManagedTenantMembers

POST /api/company-members/:id/approve
  - tenantRoles, accessGroupIds, notificationPreferences
  - Audit USER_APPROVED, USER_ACCESS_UPDATED, NOTIFICATION_PREFERENCES_UPDATED

POST /api/company-members/:id/reject
  - reason opcional, desabilita Keycloak se existir
  - Audit USER_REJECTED

PATCH /api/company-members/:id/access
  - Atualiza roles, grupos e notificationPreferences

4. SCHEMA tenant_members (campos principais)
================================================================================

firstName, lastName, whatsapp, whatsappNormalized,

timestamps, audit fields (approvedBy, rejectedBy, etc.)

Dual-write: company_members (legado) espelhado via tenantMemberRepository.

5. requestedAccess
================================================================================

CPF/CNPJ: apenas taxIdMasked + taxIdHash no MongoDB (nunca cru em logs).

8. FORMULÁRIO PÚBLICO
================================================================================

Rota: /solicitar-acesso (sem autenticação, sem init Keycloak forçado)

Campos: tipo PF/PJ, CPF/CNPJ, razão social, nome, e-mail, WhatsApp,
cargo, setor informado, motivo, consentimento operacional.

Usuário NÃO escolhe roles, grupos ou permissões reais.

10. SETOR INFORMADO vs GRUPOS REAIS
================================================================================

Setor/cargo/motivo: dados declarados em requestedAccess (apoio ao admin).
Grupos reais: accessGroupIds definidos manualmente pelo admin.
suggestGroupsFromDepartment() apenas sugere visualmente.
